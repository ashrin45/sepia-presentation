04Les logiciels

Les briques logicielles, par fonction.

Cœur data
Python ≥ 3.11
Langage unique du pipeline — parseurs, transformations, tests

Langage unique de bout en bout, choisi pour son écosystème data mature et la lisibilité du code.

Tout le pipeline — parsing binaire .smp, transformations, tests — tient en Python pur, sans dépendance système exotique à installer sur le poste.

Polars
Bibliothèque de manipulation de données en tableaux (alternative moderne à pandas) — porte les transformations bronze → silver → gold

Bibliothèque de manipulation de tableaux de données, écrite en Rust : nativement multicœur et bien plus rapide que pandas sur de gros volumes.

Traite sans difficulté les ~600 paramètres × 49 675 hémocultures en mémoire. Son évaluation différée (lazy) optimise les chaînes de transformation.

DuckDB
SQL analytique directement sur les Parquet — exploration & contrôles

Base analytique « embarquée » — comme SQLite, mais orientée colonnes.

Elle lit directement les fichiers Parquet sans import préalable : on écrit du SQL sur le lac de données local. Idéale pour l'exploration ad hoc et les contrôles qualité croisés.

Stockage & format
Apache Parquet
Format columnar compressé et typé — une table = un dossier partitionné

Format de fichier columnar : les données sont rangées par colonne, compressées et typées.

Lecture sélective (on ne charge que les colonnes utiles), gain d'espace ×5 à ×10 face au CSV, et schéma auto-décrit. C'est le standard de fait des lacs de données.

Apache Arrow
Représentation mémoire columnar — échanges zéro-copie Polars ↔ DuckDB

Standard de représentation des données en mémoire, partagé entre outils.

Il permet à Polars et DuckDB d'échanger des tables sans copie ni sérialisation (zéro-copie) — d'où des transitions quasi instantanées d'une étape à l'autre.

Partitions Hive
year= / month= / run_id= — lecture sélective sans tout charger

Convention de nommage des dossiers — year=2024 / month=03 / run_id=… — qui encode les filtres directement dans l'arborescence.

Le moteur ne lit que les partitions concernées par une requête : accès rapide sans charger toute la table.

Qualité & outillage
Git
Versioning du code et de la Rosetta Stone — analyses reproductibles

Versioning du code et de la table de correspondance (Rosetta Stone).

Chaque analyse référence un commit précis : on peut rejouer exactement le pipeline tel qu'il était à une date donnée — traçabilité complète des évolutions de mapping.

Make
Orchestration des étapes — un seul make rejoue le pipeline

Orchestrateur léger, déjà présent sur tout poste Unix.

Il décrit un graphe de dépendances entre étapes : make ne rejoue que ce qui a changé. Pas besoin d'Airflow ni d'orchestrateur lourd pour un pipeline local.

pytest
Tests & cross-checks — garde-fous sur parseurs et mappings

28 tests techniques valident les briques unitaires : paths, hash, parsing du nom, IO Parquet, idempotence du log.

14 tests métier valident la chaîne SMP de bout en bout — dont 9 sur fichiers .smp réels (DATA_exemple), avec des validations biologiques (HGB dans plage, NEUT dans plage…).

08Format propriétaire

Décodage du format binaire propriétaire .smp.

Chaque tube produit un fichier .smp — un binaire MFC CArchive, non documenté. Aucune librairie ne le lit. Le parser a été ré-implémenté intégralement, en Python pur.

  • Header de 256 octets — magic SMP\0File Ver1.0\0
  • ≈ 25 sections dont le bloc CData_ITEM
  • 606 records de 22 octets — un par paramètre mesuré
  • Les sections PII (patient, médecin, service) sont identifiées et jamais lues
# Header 256 o — magic "SMP\0File Ver1.0\0" # MFC CArchive · ~25 sections # Bloc CData_ITEM — 606 records × 22 octets : [marker 4o][value LE32][field2][field3][item_id LE16][next] ↑ valeur brute ↑ code Sysmex # Affiché = value / Divisor (appliqué en silver)

11Idempotence & traçabilité

Idempotence et traçabilité de la chaîne d'audit.

Idempotence d'ingestion · 3 niveaux
1 · Listing rapideos.walk() → (path, size, mtime) en quelques secondes même sur 30 k fichiers
2 · Comparaison au logla table ingestion_log filtre les fichiers déjà connus
3 · Hash + ingestionSHA-256 calculé uniquement sur les fichiers nouveaux ou modifiés

Run « à vide » = 5-10 s · run mensuel = quelques minutes · rattrapage historique = plusieurs heures, une seule fois.

Traçabilité d'audit · colonnes techniques
  • _source_file — nom du fichier source
  • _source_hash — SHA-256, intégrité
  • _ingested_at — timestamp UTC
  • _run_id — identifiant du run pipeline
  • _pipeline_version — version sémantique du code

Pour n'importe quelle ligne silver ou gold, on peut remonter au fichier source exact et à la version de code qui l'a produite.

17Pour aller plus loin

La phase 1 de SEPIA est une preuve de concept.

Le POC actuel entraîne un modèle sur des métriques déjà calculées par l'automate — les ~600 paramètres du fichier .smp.

Ces métriques restent dépendantes du gating de l'instrument : sur certains profils cellulaires anormaux, elles deviennent peu fiables, voire impossibles à calculer (flèches).

Scattergrams DIFF : quand les populations leucocytaires se chevauchent ou sortent des fenêtres attendues, les métriques standard sont prises en défaut.
Phase 2
Confirmation multicentrique
Rejouer le pipeline et le modèle sur deux autres centres — CHI de Montfermeil et CHI d'Aulnay-sous-Bois — pour confirmer la robustesse hors site pilote.
Phase 3
Repartir des données brutes .fcs
Calculer des métriques originales directement sur les événements cytométriques, et reprendre l'apprentissage en machine learning, voire en deep learning.
Phase 4
Étude clinique à deux bras
Comparer la prise en charge avec aide à la décision et sans aide, pour mesurer l'apport réel au lit du patient.
En parallèle
Un pipeline réutilisable
La même infrastructure s'applique à d'autres événements que le sepsis : paludisme, leucémie, et autres signatures cellulaires.
